# Runtime Context

## Glossary

- **Runtime**: the Tiny host that starts an application, owns application lifecycle, page stack, routing dispatch, global registration, and platform API dispatch.
- **Glass-easel adapter**: the internal translation layer between the Runtime and glass-easel component APIs. It is not a public dependency for other packages.
- **Render backend**: the pluggable boundary that creates, updates, and receives events for the rendered component tree.
- **Core entry**: `@tiny/runtime`, which must remain free of browser globals.
- **Browser host**: `@tiny/host-browser` (`hosts/browser`), which owns iframes, message ports, DOM canvas, page visibility, and the devtool overlay.
- **Render thread connector**: `RenderThreadConnector` lets a host create one render transport per page. `createTinyRuntime` routes page-scoped messages by page ID, bootstraps each render thread with that page's data, and tears the thread down on `onUnload`. Without a connector, a single render transport serves the whole stack (tests and simple hosts).
- **Page frame**: the host-owned render document for one page. The devtool keeps hidden page frames mounted and only toggles visibility, so back navigation does not rebuild the page from data.
- **Page lifecycle**: service-driven `onLoad/onShow/onReady/onHide/onUnload` plus render-driven `onPageScroll/onReachBottom`, host-driven `onResize`, and tabBar-driven `onTabItemTap`. Every transition is emitted as a `PAGE_LIFECYCLE` diagnostic with page identity and a monotonic sequence; `RUNTIME_STATE` carries the page stack, live/cached pages, tabBar state, and visible flags.
- **TabBar**: `app.json.tabBar` is normalized by the service. Tab pages are cached across `switchTab` (hidden, not unloaded), non-tab pages are destroyed, and `RUNTIME_STATE.tabBar` exposes visibility, selected index, style, icons, badges, and red dots to a host. The service implements `switchTab` and the standard tabBar mutation APIs; the browser host owns rendering.
- **Page stack limit**: `maxPageStack` defaults to 10 and is supplied by the host through the runtime bootstrap. `navigateTo` rejects before hiding the current page when the stack is full; the limit is echoed in `RUNTIME_STATE.maxPageStack`.
- **Bridge**: the transport-only boundary for serialization, batching, timeouts, and errors. It does not define API or rendering behavior.
- **Built-in components**: glass-easel component definitions for mini-program tags such as `view`, `text`, `image`, `button`, and `input`.
- **Runtime compatibility**: manifest-provided API namespace/aliases, registration globals, behavior scheme, and legacy opaque globals. These affect the mini-program input contract, not Tiny's fixed internal naming.
- **Asset resolution**: `RenderThreadOptions.resolveAssetUrl` is a host hook that maps app-root-relative asset paths to loadable URLs. The adapter resolves `<image src>` against the owning page/component source path and rewrites local WXSS `url(...)` values before style registration; external/data URLs and paths escaping the app root stay unchanged.
- **Style scope**: glass-easel prefixes class names with the owning page/component style scope. The render thread registers stylesheets before registering component definitions so definitions receive their scope ID; external classes from a page remain scoped to the page. Ordinary `Page` roots are always `shared`; only component-as-page roots read an explicit component `styleIsolation` and otherwise also default to `shared`. Page/component tag selectors are rewritten to `tiny-<tag>:where(.tiny-tag-<tag>)`, preserving tag specificity while preventing leakage. Every rendered element also carries the fixed generic scope marker (`tiny-scope`); selector-only rules such as `*`, `#id`, and bare pseudo-classes are anchored with `:where()` and cannot escape their page/component. Page-scope anchors additionally include the page host attribute so the page root participates without relying on a prefixed class. `:host` rules are emitted to low-priority CSS and registered before app/page/component sheets. The app stylesheet (`app.wxss` in WeChat-compatible fixtures) stays in the global scope; every app compound is explicitly anchored to the unscoped app marker, and page elements keep both scoped classes and unscoped names (the page's `extraStyleScope` is the global scope), so global app selectors match page-owned nodes. For pages using `apply-shared`/`shared` components, the compiler's app page-scope template anchors every compound to the page scope marker plus the page host attribute and marks class names for runtime expansion to `<pageScope>--<class>`; the expanded sheet is appended after the global app sheet and before page/component sheets. Those components receive the page scope as their extra scope, so app rules reach them while `isolated` and built-in internals do not match. Built-in hosts are a public global-style boundary; each built-in's private internal DOM uses an independent `tiny-builtin-<tag>` stylesheet scope. Inherited properties, CSS variables, and declared `externalClasses` cross that boundary, but app/page/component selectors cannot directly target internal implementation nodes. Runtime consumers identify app, page, component, and page-scope sheets through manifest artifact references and `pageScopeClassSign`, never through source filenames or extensions. Render-thread-connector bootstraps register only the selected page, its transitive component styles, and that page's app-scope expansion; a shared render transport still registers the full manifest because it serves the whole page stack.
