# Embedding the devtool in the website

Research and implementation note for serving `apps/devtool` as a live demo on
the GitHub Pages site.

## Goal and constraints

The site should expose a real debugger, not screenshots. The embedded instance
must:

- boot the same dual-thread runtime and `DevtoolRuntimeClient` used by
  `pnpm dev:devtool`;
- work under the Pages project prefix (`/<repo>/`), so every devtool URL has to
  be relocatable;
- work under the Vite dev server (`/`) without a second deployment;
- keep generated artifacts and fixture output out of git;
- keep the Pages artifact small. A full `compile:devtool:all` build is ~29 MiB,
  while the demo fixture alone is ~1.3 MiB including the devtool shell.

## Options considered

| Option | Result |
| --- | --- |
| Link to a separately deployed devtool | Rejected: adds a second deployment and cross-origin iframe/fetch work |
| Build the devtool into the site bundle | Rejected: React 17 duplication, thread HTML would have to be generated by Vite, and the runtime's iframe URLs are document-based |
| Copy the static devtool build at site-build time | Chosen: the devtool is already a static SPA plus two thread documents; the site only needs to publish it under one directory |
| Commit prebuilt devtool artifacts | Rejected: generated output does not belong in git and would drift from source |

The chosen model is a same-origin iframe:

```text
website/#/devtool
  └── iframe ./devtool/index.html
        ├── next-service.html?app=demo
        └── next-render.html?app=demo
              └── runtime/apps.json
                  runtime/apps/demo/generated/{manifest,service,render,templates,styles}
```

Both thread documents are same-origin, which is required for
`fetch`/`import()` of the generated artifacts and for transferring the
`MessageChannel` ports with `postMessage`.

## Why the devtool had to become relocatable

Before this change, the panel, registry, and thread entries used root-absolute
paths (`/runtime/apps.json`, `/next-service.html`, `/runtime/apps/<id>/generated`).
Those work in `rspack serve` at `/` but break under `/tiny/devtool/`.

The fix follows the document base instead of the server root:

| Location | Before | After |
| --- | --- | --- |
| `config.js` | `/runtime/apps.json` | `./runtime/apps.json` |
| `appRegistry.js` | `/runtime/apps/<id>/generated` | `new URL('./runtime/apps/<id>/generated', location.href)` |
| `runtimePanel.jsx` | `/next-service.html` | `new URL('./next-service.html?...', location.href)` |
| `runtimeService.js` / `runtimeRender.js` | `/runtime/apps/...` | `generatedBaseFor(appId)` (document-relative) |
| rspack `output.publicPath` | `/` | `./` in production, `/` in dev |

`generatedBaseFor()` is evaluated inside each thread iframe, so the service and
render documents resolve the generated app relative to their own directory.
Passing an absolute URL to the `new Function(..., 'import(url)')` helper also
removes ambiguity about dynamic-import base URLs.

## Build integration

`scripts/build-site-devtool.mjs` is the single entry point:

1. If `tools/cli/dist`, `packages/runtime/dist`, or `hosts/browser/dist` are
   missing, run `pnpm build:glass-easel`.
2. Compile selected fixtures (default `demo`) into
   `website/.cache/devtool/runtime`.
3. Write a reduced `apps.json` for that fixture set.
4. Run the devtool production build with:
   - `NODE_ENV=production`
   - `TINY_DEVTOOL_RUNTIME_ROOT=website/.cache/devtool/runtime`
   - `TINY_DEVTOOL_OUT_DIR=website/.cache/devtool/dist`
5. Copy the build to `website/.cache/site-public/devtool`.
6. Validate that the expected HTML, registry, and thread artifacts exist.

`website/vite.config.js` points `publicDir` at `.cache/site-public`. During
`pnpm site:dev`, Vite serves `/devtool/index.html` from there. During
`pnpm site:build`, Vite copies it to `website/dist/devtool/`. Nothing outside
`website/.cache/` and `website/dist/` is produced, and both are gitignored.

The iframe uses `./devtool/index.html`, not `./devtool/`. Vite's dev server
serves the public directory's `index.html` at the explicit file URL, but its SPA
fallback answers a bare directory request with the website shell. The explicit
file also works on Pages.

## Entry points

- Nav/footer link: `#/devtool`
- Home page CTA and live-devtool card
- `website/src/pages/Devtool.jsx`: embedded iframe, build chain, path contract,
  and limitations
- Direct link inside the page opens `./devtool/index.html` in a new tab

## Validation

```bash
pnpm site:build
pnpm site:check
pnpm site:preview
```

`scripts/check-website.mjs` now checks the site shell plus
`devtool/index.html`, `devtool/next-service.html`, and
`devtool/next-render.html` for root-absolute asset URLs, scans the emitted
bundles for root-absolute devtool/runtime URLs, verifies the demo runtime
manifest, and requires the generated `service.js`, `render.js`, and
`templates.js`.

Manual browser validation used a 1400×1000 Chromium page against the Vite
preview server: the iframe reports `status: running`, the page stack starts at
`pages/todos/todos`, the demo body renders `Tiny Glass-easel P0`, and there are
no console errors or failed requests.
